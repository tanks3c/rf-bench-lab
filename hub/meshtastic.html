Course mission

By the end of this course you should be able to:

  • Explain how a Meshtastic mesh works.
  • Configure a node without changing settings blindly.
  • Select the correct device role.
  • Understand primary and secondary channels.
  • Send broadcasts and direct messages appropriately.
  • Interpret acknowledgements and failed transmissions.
  • Monitor the mesh without adding needless airtime.
  • Operate on the Florida Mesh using its regional conventions.
  • Understand LoRa presets, frequency slots, hop limits, and airtime.
  • Recognize basic RF and antenna problems.
  • Configure and verify MQTT.
  • Tell RF traffic from MQTT traffic.
  • Use logs to see what the device is actually doing.
  • Separate normal warnings from faults that need action.
  • Back up configuration and update firmware safely.
  • Maintain a mobile, stationary, or gateway node.
  • Troubleshoot systematically instead of changing settings at random.

BLOCK I

Mesh operator

M1What Meshtastic actually is

Understand what the radio is doing before learning the app.

Node

A node is one Meshtastic radio on the network. The Heltec V3 is a node. A node can transmit, receive, and relay packets, talk to a phone or computer, keep a database of other nodes, and optionally bridge traffic to MQTT.

Mesh

Nodes relay for each other, so you do not need a direct radio path to every destination. The hop limit caps how many relays a packet may take.

Your node → another node → another node → destination

LoRa

LoRa is the long-range RF method that carries Meshtastic packets. Meshtastic is not cellular, normal Wi-Fi messaging, Bluetooth messaging, or MQTT. Bluetooth and Wi-Fi connect clients and services to the node. LoRa is what connects the radio mesh.

Packet

The formatted unit moving through the network. It can carry text, node info, position, telemetry, routing data, or acknowledgements.

Broadcast vs direct message

A broadcast is for the whole channel. A direct message targets one node. A broadcast acknowledgement does not confirm that a specific person read your message.

Practical exercise 1

Qualification standard: you can explain the difference between your phone, your node, and the mesh.

M2Channels

Separate the LoRa radio configuration from a Meshtastic message channel.

Meshtastic supports up to eight channel slots, indexed 0 through 7. Channel 0 normally holds the primary channel.

Primary channel

Only one channel is PRIMARY. Periodic broadcasts such as position and telemetry normally go out on it.

Secondary channels

Secondary channels let more groups share the same physical LoRa configuration. Changing channels does not give each channel its own frequency. Every active channel uses the node's one modem configuration.

What defines a message channel

  • Channel name (case-sensitive)
  • PSK, which controls channel encryption
  • Channel role
  • Uplink setting
  • Downlink setting

Operating rules

Passive monitoring

Transmit nothing. You do not need to announce that you are listening.

Mobile monitoring

Monitor normally. If you must announce, use a general chat channel and keep it short. Do not keep broadcasting location or status by hand to show you are present.

Static monitoring

A stationary node can stay online and relay according to its role. Stationary does not mean it needs ROUTER or REPEATER.

Equipment testing

Use testing, a private test channel, or an accepted local procedure. Never test on emergency.

A community member answering "test" or "ping" with a tapback is useful evidence someone received you. It is a community habit, not a Meshtastic protocol feature.

M4Messages, ACKs, and tapbacks

Know what a success indicator actually proves.

The Android app shows separate stages: queued by the app, queued by the radio, acknowledged by at least one mesh node, acknowledged by the intended DM recipient, and failed or not acknowledged.

For a broadcast, Meshtastic gets an implicit acknowledgement when it hears another node rebroadcast the packet. That proves mesh participation. It does not mean a person read it. For a direct message, the destination node returns a real acknowledgement.

ACK

Network evidence.

Tapback

A user or application response.

Practical exercise 2

Send one short message on an appropriate test channel. Record the time sent, the channel, whether an ACK appeared, how long it took, and whether anyone replied or tapped back.

Do not resend just because nobody answered socially.

M5Device roles

One of the most important operating topics.

RoleWhat it doesWhen to use it
CLIENTSends, receives, takes part in relaying, works with apps.The default for most operators.
CLIENT_MUTECommunicates but does not relay other nodes' packets.Several of your nodes sit close together, such as a roof node, a desk node, and a portable on one property.
CLIENT_BASEPrioritizes rebroadcasting your other personal (favorited) nodes.A well-placed home station supporting your weaker personal gear.
ROUTER / REPEATERInfrastructure roles.Only for planned infrastructure. Not because a node is stationary, on a roof, has a better antenna, stays powered, or you want more range.

Florida Mesh recommends CLIENT, CLIENT_BASE, or CLIENT_MUTE for normal nodes. Meshtastic's own docs warn that using ROUTER or REPEATER unnecessarily can cause serious network issues.

Qualification question: you install a Heltec V3 permanently in your attic. Should you change it to ROUTER? No. A stationary location alone does not justify an infrastructure role.

BLOCK II

Radio operator

M6Region, preset, frequency, and hops

Region

The device must use the correct regulatory region. The example log shows US. Meshtastic documents the US LoRa range as 902 to 928 MHz.

Modem preset

Presets set the major LoRa traits: speed, range, airtime, and network capacity. The default is LongFast. Slower presets use more airtime, so slower is not automatically better.

Florida presets

  • LongFast for most of Florida.
  • MediumFast for designated parts of the southeast coast.
  • Brevard County is an overlap, dual-preset area.

Check the Florida Mesh regional settings before changing your preset.

Frequency slot

The slot sets the actual RF frequency inside the band. The example log reports 906.875 MHz, the North American LongFast default. Do not change slots casually. Two radios with matching channel names and keys still fail if their LoRa settings differ.

Hop limit

The default is 3, and Meshtastic strongly recommends leaving it there unless you have a specific need. The example log shows HopLim=3 throughout.

Practical exercise 3: baseline configuration sheet

Record these from your node and keep the sheet. It is your known-good baseline.

Saved only in this browser. Do not enter keys, passwords, or your location.

M7RF and antenna fundamentals

Many apparent Meshtastic problems are really RF installation problems.

  1. Never transmit without the correct antenna attached. Meshtastic warns that reflected RF energy from a missing or badly mismatched antenna can damage the radio.
  2. Correct frequency matters. For US and Florida use, fit an antenna designed for the 915 MHz band.
  3. Height and surroundings matter. Buildings, terrain, vegetation, orientation, line of sight, and Fresnel-zone blockage all affect range. A better location often beats a higher-gain antenna.
  4. Coax has loss. A long cable can eat the gain you wanted from an outdoor antenna. Putting the whole node outside often works better than a long run from indoors.
  5. VSWR does not tell the whole story. A VNA shows whether an antenna is reasonably matched. It does not prove the antenna radiates efficiently.

Range-test procedure

Record the test location, distance, ACK or no ACK, direct or multi-hop, RSSI and SNR if available, antenna, and antenna position.

Change one thing at a time. If you change antenna, preset, power, and location together, you cannot know which change helped.

The RF Bench Lab's link budget module has a Meshtastic preset for working through LoRa range math.

M8RSSI, SNR, and noise

RSSI

Received signal power.

Noise floor

Background RF energy at the receiver. More negative means a quieter environment.

SNR

How far the signal stands above the noise. LoRa can decode signals with negative SNR.

Do not judge a Meshtastic link from RSSI alone. The apps expose signal info, telemetry, traceroute, and local stats that help judge RF quality.

One local-stats sample in the example log shows channel utilization near 0%, TX airtime near 0.05%, and a noise floor near −100 dBm. That is a quiet moment, not proof the channel is always quiet.

BLOCK III

MQTT gateway operator

M9What MQTT changes

MQTT links Meshtastic networks over IP. A node with Wi-Fi, Ethernet, or client-proxy connectivity can send packets to an MQTT broker and receive permitted traffic back. That creates two paths that can coexist:

RF path: node → LoRa → other radio nodes
Internet path: node → Wi-Fi or client → MQTT broker → other gateways and nodes

M10MQTT uplink vs downlink

Mandatory knowledge.

Uplink

Mesh → MQTT. Your node forwards channel traffic toward the broker.

Downlink

MQTT → Mesh. Broker traffic can be delivered to the node and channel.

Both are set per channel. Florida Mesh's gateway configuration documents different policies per channel:

ChannelUplinkDownlink
Primary (LongFast)OnNormally off
FloridaMeshOnOn
emergencyOnOn
testing, weatherOnNormally off

M11Reading MQTT in a log

MQTT connected proves the device reached the broker at that moment. After a test message, the example log shows an MQTT publish to the FloridaMesh topic:

phone → local node → MQTT module → Florida broker

Packets marked via MQTT prove broker downlink traffic is arriving.

Critical distinction

MQTT Publish proves your node handed a packet to MQTT. It does not prove another person received it, another radio heard it over RF, or anyone read it or will reply.

MQTT connected ≠ RF path confirmed. Know which system you are testing.

M12Proper MQTT test method

Decide what you are testing first. These are four different tests.

TestQuestionEvidence
ACan my device connect to MQTT?MQTT connected
BCan my device uplink?One test packet and a matching MQTT publish
CCan I receive downlink?Received packets marked as arriving through MQTT
DCan another person or node interact with me?A short tapback or reply through the community test procedure

Do not keep transmitting the same message once Test A has already answered Test A.

M13Florida Mesh MQTT configuration

LoRa

  • Correct regional preset
  • Hop limit 3
  • OK to MQTT on

MQTT

  • Florida broker address
  • Your own account credentials
  • Encryption on
  • JSON normally off
  • Florida root topic
  • Map reporting as appropriate

For mobile feeders, Florida Mesh documents turning on Proxy to Client so the radio can use the phone's connection. For long-term stationary feeding, a Wi-Fi or Ethernet feeder is better than relying on a Bluetooth-tethered phone.

Current values, including the broker address and account sign-up, are in the Florida Mesh configuration guide ↗. Florida Mesh requires an account to feed MQTT.

BLOCK IV

Device maintenance

M14Firmware management

Meshtastic recommends the latest Beta firmware for most operators. Alpha builds trade stability for newer features.

For ESP32 devices like the Heltec V3, the Web Flasher ↗ is the normal method. Use Chrome or Edge and connect by USB.

Back up first. The Python CLI can export the configuration with meshtastic --export-config. A full wipe and reinstall can erase configuration, channels, and keys.

Maintenance principle

Do not update just because a version number changed that morning.

  1. Review the release information.
  2. Decide whether it matters for your hardware and use.
  3. Back up.
  4. Verify the correct hardware target.
  5. Flash or update.
  6. Verify region and channels.
  7. Verify messaging.
  8. Verify MQTT if used.
  9. Keep the backup.

M15Reading a Meshtastic log

A debug log is easier once you sort entries by subsystem. Common tags:

[RadioIf] [Router] [ServerAPI] [DeviceTelemetry] [Power] [WifiConnect] [mqtt] [WebServer] [Screen]

A WARN or ERROR string is not proof the radio failed. Ask: which subsystem generated it, and did operation continue afterward?

M17Items worth monitoring

Low heap

Low heap (... bytes), skipping HTTPS processing comes from the WebServer subsystem. The firmware protects itself by skipping HTTPS work when memory runs low. It does not prove LoRa failed. It matters when it comes with an unstable web interface, app disconnects, unexplained reboots, MQTT instability, or other memory symptoms. Record it and correlate before changing configuration.

NodeDB capacity

When the database reaches about 200 nodes, an old entry is removed. That is normal capacity management. Favoriting important nodes helps, because favorites get special retention.

Wi-Fi disconnects

  1. Did Wi-Fi reconnect?
  2. Did MQTT reconnect?
  3. Was LoRa still operating?
  4. Was it a network change or a real node reset?

Separate an IP networking problem from a LoRa problem.

Missing configuration files

Boot messages may show errors for files such as the UI configuration. In the example capture the node boots and runs anyway. Investigate only if the related function fails, not because the word ERROR appears.

BLOCK V

Operating procedures

M19Pre-operation checklist

Before taking a node into service:

M20Mobile operations SOP

  1. Use CLIENT unless there is a defined reason not to.
  2. Confirm the regional preset before travel.
  3. Keep the antenna upright and clear of major obstructions where practical.
  4. Avoid unnecessary automated broadcasts.
  5. Use the normal mesh for real communication.
  6. Use testing or private channels for deliberate tests.
  7. Never use the emergency channel for routine status or testing.
  8. For mobile MQTT, client proxy may be appropriate.
  9. Remember that phone and Bluetooth internet is separate from LoRa.
  10. Record meaningful range observations instead of sending repeated test traffic.

M21Static / home node SOP

  1. Favor height and RF position.
  2. Use a reliable power supply.
  3. Keep coax short if you use an external antenna.
  4. Start with CLIENT.
  5. Consider CLIENT_BASE when it specifically supports your personal nodes.
  6. Use CLIENT_MUTE for redundant nearby nodes where it fits.
  7. Do not pick ROUTER or REPEATER just because the node is permanent.
  8. If it feeds MQTT, verify Wi-Fi and broker connectivity.
  9. Check uptime and unexpected resets periodically.
  10. Keep a configuration backup.

M22Troubleshooting workflow

Never start troubleshooting by changing five settings.

  1. Define the failure. Bad: "Meshtastic isn't working." Good: "I receive RF messages but my node is not publishing to MQTT."
  2. Find the layer.
    LayerQuestion
    Hardware / powerDoes the node boot reliably?
    Client linkCan the phone or computer connect?
    LoRaCan you receive or transmit RF packets?
    ChannelAre name, key, and settings correct?
    RoutingCan the target be reached?
    InternetDoes the node have Wi-Fi or client connectivity?
    MQTTIs the broker connected and publishing?
  3. Check the log for the relevant subsystem.
  4. Change one variable: move the antenna, reconnect Wi-Fi, fix one channel setting, restart MQTT, or try another power cable.
  5. Retest and record the result.
  6. Escalate only when the evidence requires it. Do not factory-reset a working radio because one message lacked an ACK.

M23Traceroute

Traceroute shows the path used to reach another node. Modern firmware adds SNR along the path. Use it to check reachability, see which intermediate nodes took part, compare forward and reverse routes, and find a weak hop.

Traceroute creates traffic. Use it deliberately, not continuously.

M24Florida weekly mesh net

Florida Mesh runs a weekly net on Mondays: 7:00 PM local in Northwest Florida, 8:00 PM local in North, Central, and South Florida. It runs two hours. The Meshtastic net is on the default public primary channel.

(NAME) - (CITY) #FLMeshNet message 1

Increment the message number with each check-in. The net exercises infrastructure and measures range, which makes it a good controlled training environment: known activity, many stations, ACK comparisons, gateway reception data, and geographic observations.

Security module: logs and credentials

Debug logs can contain MQTT usernames and passwords in plain text. Treat every log as sensitive.

Before sharing a log:

  • Redact MQTT usernames where appropriate.
  • Redact MQTT passwords.
  • Redact Wi-Fi credentials if present.
  • Check for precise location information.
  • Check for private channel names and keys.

If a password has ever appeared in a shared log, rotate it through Florida Mesh's MQTT account procedure and do not reuse it.

Operator decision matrix

"I don't see any messages."

  1. Correct region
  2. Regional preset
  3. Frequency slot
  4. Antenna
  5. Channels
  6. Physical location
  7. Whether anyone nearby is actually transmitting

"My message isn't acknowledged."

Do not change configuration first. Check:

  1. Whether reachable nodes exist
  2. RF environment
  3. Antenna and location
  4. Whether retries occur
  5. Whether other messages work

"MQTT isn't working."

  1. Internet connection
  2. MQTT enabled
  3. Server
  4. Credentials
  5. Root topic
  6. Channel uplink and downlink
  7. Log for MQTT connected
  8. Log for publish and received-topic events

"The map doesn't show me."

Check Florida Mesh's requirements:

  • OK to MQTT
  • A feeder in range, or your own gateway
  • Map reporting configuration
  • Location precision
  • MQTT configuration

"I have poor range."

  1. Antenna frequency
  2. Antenna quality
  3. Antenna orientation
  4. Height
  5. Buildings and terrain
  6. Cable loss
  7. SNR and noise
  8. Actual path testing

Do not start by raising the hop limit.

Operator qualification standard

You are ready to operate your Meshtastic equipment on your own when you can reliably answer:

What path is this packet using? Phone or client, local node, LoRa RF, relay, MQTT, or some combination.

You are ready to maintain it when you can also answer:

What changed, what evidence do I have, and which subsystem should I test next?

That distinction, more than memorizing every setting, is the core skill of a competent mesh operator.
